## Windows text runner and NCM XSum preview - 20 October

The native Go worker now supports Windows AMD64 with fixed, signed engine/connector recipes and exclusive state ownership. Windows Job Objects bind processes before they run and contain descendants; explicit backend switching confirms the old tree has stopped. Runtime files, model weights and dependency directories are hashed before launch. This is a development ZIP with preparation scripts, not a signed installer or Windows Service. Linux systemd adoption remains supported.

The prepared backends are pinned llama.cpp Vulkan for an existing GGUF and the released HazyResearch NCM XSum checkpoint, CPU by default. NCM uses `hearth.summary.v1` under the existing `text.summarize` permission. It accepts one fresh article of at most 512 GPT-2 tokens and returns at most 48 tokens as a final answer. It rejects history, images, tools, client system prompts and unsupported sampling controls; private recalled context is excluded. Typed provider metadata and ID/model/revision-bound receipts distinguish it from a chat LLM. The Admin provider form and readiness checks understand this protocol. NCM routes require Ordered selection. Backend switching is explicit in Workers with Resident policy; universal text/audio queues are still unimplemented.

Initial real Windows runs produced a reply from an existing 27B GGUF through llama.cpp and a CPU NCM result. The NCM sample invented details, so it remains experimental, with no faithful-summary, compaction or speedup claim. Native Windows worker/connector tests and TypeScript/both UI builds pass. On the designated head with isolated test storage, 22 focused checks passed and one opt-in check skipped, covering NCM registration/probing, fresh private summaries, context rejection, existing worker admission, multi-provider behavior and inference timeouts. Production data was not used as a fixture. These bounded observations do not close any of the 61 release gates. See [setup, switching and rollback](../operations/WINDOWS_RUNNER.md) and [upstream pins/notices](../operations/NCM_THIRD_PARTY.md).

The matching API/schema and UI update was deployed to the designated existing head after idle checks, source-baseline comparison and a private database/source/image rollback. A real Windows worker was enrolled with two separately authenticated TLS connections in one resource pool. Both backend switches were observed; the head verified LLM chat, streaming and native tools and an NCM summary receipt. Chat/coding now prefer the Windows LLM; Ordered summarization supports the selected NCM or LLM. The LLM was left resident. The old external connection remains available for rollback; Vision is not requalified on the new text runner. Trusted HTTPS readiness and served asset comparisons passed on both surfaces. Final NCM context/output-budget checks passed **15 tests** on isolated head storage; five compiled Linux manager regressions also passed.
