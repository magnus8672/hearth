# Lasting provider qualification

The previous implementation invalidated successful provider evidence after one hour. That timer was a conservative development shortcut, not an observed service failure. It has been removed from routing, image admission and the administration UI. No database migration or credential replacement is required; old expiry timestamps are ignored and new successful probes store no expiration.

Initial registration still runs an actual capability probe. Successful features stay qualified until the connection/model/trust configuration changes, an administrator disables the target, a transport or provider job fails, or a changed media manifest is observed. Text output limits, user cancellation, revoked user sessions and model planning-format mistakes do not by themselves invalidate provider health. Unknown executions remain fenced until the backend is known idle; no error triggers automatic prompt replay or an implicit fallback generation.

At head startup, the admin API checks previously qualified targets automatically in its configured farm using its restricted application database role. It temporarily fences idle targets while checking their connections. OpenAI-compatible providers receive read-only model-list and, when configured, LM Studio loaded-instance checks. Image, speech and transcription providers must return the same qualified information, including model, manifest, features and limits. These checks neither generate content nor load or swap models. Existing vision qualification is retained. The startup check is not a fresh model-quality or weight-identity attestation for an external OpenAI-compatible server.

Independently booting providers have a two-minute retry grace period for these read-only checks. Busy or uncertain resource groups are deferred without clearing execution receipts. Changing settings, revoking HTTP consent or disabling a target wins over an in-progress check. A failed startup check or execution puts the target in a visible failed state; after repairing the service, use its existing Verify control for a full capability probe. Previously failed, disabled and never-qualified targets are not silently enabled by a restart.

The head still validates HTTPS certificates and scoped HTTP approval on each connection. User sessions, privileged grants and TLS certificates retain their own expiration rules; only the one-hour provider qualification deadline was removed.

The new [Ubuntu audio VM setup](../operations/AUDIO_VM_SETUP.md) provides independently installed speech/transcription services, digest-pinned model preparation, boot startup and HTTPS identity/renewal. It does not migrate the head database or change capability bindings. The active head now runs on ESXi; the full existing-farm migration/restore workflow, signed managed enrollment, general fleet heartbeat/recovery policy and live Switchyard routing remain open.

Evidence is recorded under [provider lifecycle](../../evidence/provider-lifecycle/2026-09-13/validation.json). Startup/expiry/error tests use actual restricted-role PostgreSQL with explicit provider fixtures; browser interaction tests use fixture identity/API data. Audio VM qualification performs real CPU inference over verified HTTPS in the Ubuntu WHPX guest, not on ESX or through a physical microphone. All 61 release gates remain open.
