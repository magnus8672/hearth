## How to read the tables

| Status | Meaning |
|---|---|
| Working slice | Implemented with recorded real integration evidence within stated limits; the larger design requirement may still be incomplete |
| Partial | Some operational behavior exists, with material functions or qualification missing |
| Foundation | Schema, policy, adapter interface or bounded fixture/probe exists; the product workflow does not |
| Missing | No usable end-to-end implementation found for this requirement |
| Proposed | Optional research or extension, not a completed baseline capability |

“Configured,” “observed” and “verified” remain separate. A model transport probe is not a specialist quality benchmark. Existing-provider connectivity is not managed worker enrollment. Browser fixtures test presentation and interactions; separate real-Keycloak evidence tests actual sign-in.

## Same-type provider registration and resident models

**User-reported 13 September 2026; implemented local correction, physical LAN acceptance open.** The original report was that the user could not find a working way to register more than one model server in Administration. [The correction](MULTI_PROVIDER_RESIDENCY.md) adds explicit onboarding, topology controls and an LM Studio loaded-instance check; the acceptance cases below remain the full qualification target. The required topology includes three or four LM Studio instances on different machines, each retaining its own selected resident model. The same rule applies to every supported provider family, including image, audio and geometry services as their adapters arrive. hearth must support many independent server instances of one type and many-to-many capability-to-model assignments within explicit capacity limits.

Provider type identifies an adapter/protocol; it is not a unique server slot. A server connection has its own address, credentials and trust. A model/pipeline target belongs to that connection. Several capabilities may use one target, and one capability may have several compatible targets. Identical model identifiers on different servers are distinct targets. Independent GPUs have independent resource groups; models sharing the same physical GPU share admission. Adding another server must not replace an existing one or cause unrelated machines to wait on a single default group.

**Preferred deployment, clarified in the subsequent user follow-up:** distribute different specialist models across machines so they remain loaded concurrently, then route work to the machine with the required qualified model. Multiple models on a single machine are optional. The two services currently sharing the development GPU prove integration only; they do not define the intended farm topology. The normal routing path should avoid downloads, cold loads and evictions, with lifecycle changes handled through explicit management plans. See [the placement and latency policy](../adr/0006-managed-and-external-providers.md#distributed-residency-is-the-default).

The following is an illustrative topology, not a discovered or configured farm:

| Server instance | Resident model / pipeline | Capability assignments | Resource group |
|---|---|---|---|
| LM Studio on office laptop | Model A | Conversation, writing, summarization | Office GPU |
| LM Studio on workshop PC | Model B | Coding, code explanation | Workshop GPU |
| LM Studio on spare laptop | Model C | Planning, extraction | Spare laptop GPU |
| LM Studio on second spare | Model A, an independent copy | Additional conversation/writing choice | Second spare GPU |
| Image service on graphics PC | Pipeline D | Image generation | Graphics GPU |

### Original source observations before the correction

- [The database](../../services/api/migrations/versions/0003_existing_provider.py) keys connections by farm/address and targets by connection/model. It has no one-provider-per-type uniqueness constraint. [Registration](../../services/api/src/hearth/providers.py) currently bounds the farm to 32 targets; [assignments](../../services/api/src/hearth/routing.py) allow up to eight ordered choices per capability. These bounds should be explicit, rather than mistaken for a single-instance product model.
- [The form](../../packages/ui/src/providers.tsx) can submit a new connection, but has no explicit **Add server** action. It combines adding a server, registering a model and editing an existing connection; completed submissions retain most field values. The initial resource-group value is always `Shared local GPU`. Those are confirmed source observations, not proof of the exact failure the user encountered.
- Existing [browser fixtures](../../tests/browser/chat.spec.ts) include two preconfigured models and route editing; [API tests](../../tests/integration/test_capability_routes.py) cover multi-target ordering and independent-pool admission. They do not establish a successful user journey adding four same-type servers from scratch on separate machines.
- Network providers still require verified TLS or the authenticated connector. An address/trust rejection must explain the actual cause and recovery; it must not look like a limit on provider count. The user's exact failing action/error has not yet been reproduced, so neither a protocol uniqueness bug nor TLS as the cause is confirmed.
- An external model list or echoed model name does not prove VRAM residency. Requests may trigger a backend's automatic model loading unless its configured behavior is qualified. The existing registration/probe therefore does not establish the promised absence of model swaps.

### Required correction and acceptance

1. Provide a persistent **Add server** entry point, a separate **Add model to this server** action where supported, and an unmistakable edit mode. Adding a server starts with fresh fields and never changes an existing connection. Keep server identity/address, protocol, models, assignments and resource group visible together.
2. Add four servers of the same supported type through the actual admin flow, with distinct addresses and credentials/trust where configured. Reload and sign in again; all four remain. Repeat a model identifier on two different servers without a collision. Cover adding while an existing connection is selected for editing.
3. Assign several capabilities to one model and give another capability multiple ordered targets across machines. Adding, editing, disabling or reverifying one server preserves unrelated targets, credentials, assignments and historical route receipts. Duplicate registration of the exact existing server/model reports a clear conflict without overwriting it.
4. Make resource grouping a deliberate host/GPU choice. Different machines can serve independent requests concurrently; services using the same GPU share its slot. A generic prefilled name must not silently serialize the whole farm. Prove both cases with actual dispatch receipts, plus stale-edit and occupied/unknown-pool regressions.
5. Route only to a target that is qualified for the requested capability and configured residency policy. hearth must not ask an externally managed server to load, unload or swap a model merely to satisfy a route. Verify the backend's resident-only behavior or leave residency unknown; require explicit operator opt-in for future lifecycle control. During the multi-host test, observe loaded models before and after registration probes and routed requests, recording any backend-triggered load or eviction as a failed residency case.
6. Apply this instance/model/binding design to all provider adapters, with contract/UI coverage for multiple image services as well as text services. Geometry and semantic memory adapters remain unavailable; speech, private vision and English transcription now have executable profiles. Do not mark the flow complete until the same-type registration, routing, independent capacity and resident-model behavior are demonstrated together.
7. Demonstrate concurrent requests reaching the intended resident models on separate machines. Record the selected target/host, resource group, routing/admission time, queue time, first-output latency and any load/eviction events. Keep residency observable before and after the run; a fast second request alone does not prove the first avoided loading. Treat staged media profiles separately and record their qualified startup cost. Report measured responsiveness rather than promising network line-rate inference.

The initial audit changed no application code. The subsequent implementation and local tests are recorded in [multiple providers and residency](MULTI_PROVIDER_RESIDENCY.md). Actual UI-to-physical-LAN qualification remains open; layered browser fixtures and loopback servers do not close that acceptance case.
